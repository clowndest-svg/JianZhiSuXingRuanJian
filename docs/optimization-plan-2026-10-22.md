**三、A01—A14 的实施方法与验收标准**

**A01：把 HTTP 与实时连接的会话生命周期统一。** 票据绑定具体登录会话标识与鉴权版本；建立连接时检查会话有效性，发送、已读、通话信令处理前复核必要状态。封号、改密、退出、撤销会话时发布失效事件，关闭对应连接并清理通话。单会话退出不应误踢其他有效会话；账号封禁才覆盖全部会话。Redis 不可用时应保持保守授权语义，不能仅靠 pub/sub 决定安全性。

验收：先连接再封号、先连接再撤销、先取票再退出、改密、会话到期、多设备同时在线六类场景；失效会话不得再读写或发起通话；有效会话不受误伤；客户端能解释下线原因；检查数据库确实没有新增消息。

**A02：改为可撤销的后台会话。** 使用随机会话 ID，服务端存哈希、操作者、创建/最后活跃/绝对过期时间与撤销状态；退出必须撤销服务端记录。逐步替换共用“console/script”身份为可追踪的命名账号；脚本凭据独立、可轮换、按用途授权。保留现有 Secure/HttpOnly/SameSite 和来源校验。若只有一个运营者，先做单管理员会话与审计，不需要复杂 RBAC 平台。

验收：旧 Cookie 退出后为 401；停用或轮换凭据能撤销相关会话；空闲和绝对过期分别验证；审计记录明确是谁操作。服务端主动失效原则参见 [OWASP 会话管理指南](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)。

**A03—A04：建立一份显式字段与导出策略。** 为列表、详情、个人导出、会话合规导出分别定义输出字段，不再自动继承数据库新增列。共用消息投影，清除撤回正文、引用摘要及不应返回的媒体信息；普通个人导出和管理会话导出分别写清范围。用户导出按主键去重、设置边界与截断提示；导出记录操作者、对象、原因和数量，避免把导出正文放进审计。Directus 明确配置集合、字段与行过滤；新表新列默认无权限。部署前用策略账号测试 `fields=*`、指定敏感字段、关联展开、CSV/JSON 导出。

验收：添加未知字段后仍不出现在响应；所有入口的撤回消息一致；推送凭据和邀请码哈希不可读；明确测试超管与日常角色的不同边界。不能把 Directus 数据库可写挂载误当成底层隔离，限制仍依赖平台权限。

**A05：业务修改与成功审计同事务提交。** 将封禁、解封、改名、撤销会话、重置密码、注销改为复用 `audit_in()`；失败审计在事务回滚后独立记录，不能把失败审计再写入即将回滚的事务。文件、备份等跨事务动作采用任务状态和幂等操作 ID，区分“已提交”“执行中”“部分完成”“失败”，失败时不得盲目重做。

验收：分别注入业务 SQL 失败、审计插入失败、响应丢失和重复点击；要么两者同时成功，要么一起回滚；跨资源动作可查询真实结果。

**A06：强更门增加发布约束与真实回读。** 服务端拒绝高于已核验可安装版本的最低版本，明确当前清单、实际生效值、override 和受影响构建分布。写入使用锁、期望旧值和唯一临时文件；写后等待应用回读一致，失败返回具体状态并提供受审计回退。展示分阶段策略：提示更新→观察安装→必要时停用旧版。安装包存在、哈希、签名、升级安装通过后才考虑抬门。

验收：超出发布值、非法值、并发修改、读回不一致、包不可下载均不能显示“成功生效”；保留明确的紧急刹车。当前生产 override=0 维持现状，不能在本轮审查中顺手抬门。

**A07、A10：统一注销依赖图与媒体生命周期。** 收集帖子、评论、点赞、@、通知、会话、共享目标等直接与间接引用，补齐没有外键但有业务关联的表。删除计划签名/版本与实际执行快照一致，进入写事务后再次校验。媒体按引用关系生成清理任务，覆盖头像、周期照、帖子、评论、私信、个人表情及缩略图；共享引用还存在时保留文件。数据库提交后异步幂等删除，失败可重试、可观测。备份历史副本按保留期处理，界面明确说明。

验收：两个账号交叉评论/点赞/@、引用消息、共享目标、媒体重复引用、并发新内容、删除中断、重复执行；删后外键异常为零、其他账号无越界删除；媒体清理有实际数量和失败清单。孤儿扫描只能先报告/隔离，不能直接接上永久清理。

**A08：改为真正的恢复流程。** 首选有有效期、单次消费的重置链接或验证码；若保留临时密码，首次登录只能完成改密，不能直接获得长期完整权限。配合撤销旧会话、尝试次数限制与审计；避免管理员长期掌握用户密码。

验收：凭证第二次使用失败、过期失败、错误尝试受限、成功后旧会话与旧口令失效、邮件失败不伪报送达。先评估旧客户端兼容，必要时对不能完成强制改密的旧版给升级引导。

**A09：后台可遍历、可检索。** 用户、反馈、举报、审计统一 cursor/limit/more/next_cursor；反馈补类型、构建号、时间筛选，举报补处理状态与对象类型，审计补对象与动作筛选。保留筛选、滚动位置与已选详情；列表和统计分别给 loading/empty/error，单个健康接口失败不让全部看板消失。

验收：每类造至少 120 条数据，翻页无遗漏/重复；处理中新增记录仍稳定；关键词筛选与翻页组合正确；总量与当前页数量分开表达。会话导出 5,000 条上限需明确“已截断”或提供分批导出，不能静默当作全部。

**A11：社区批量查询。** 一次取页面主键与作者，批量获得作者头像、点赞、关注、收藏与收藏数后组装；避免每卡重复查用户和档案。根据实际查询计划补组合索引，保留游标分页，防止 JOIN 放大卡片数量或 COUNT 错误。

验收目标：12 条列表的 SELECT 从 73 次降到不超过 8 次（不含鉴权，目标需在实现后实测）；不同作者、相同作者、无头像、已注销作者、互关与收藏状态一致；10 万帖子/百万级互动的隔离样本检查查询计划与并发读写。

**A12：离线记录保存发生时间。** 草稿增加 `occurred_at`、本地日期/时区、创建时间、原始 request_id 与状态；服务端将“记录发生日”和“收到请求日”分开。餐食、训练、补录共用业务写入层，防止跨端校验漂移。旧草稿缺少日期时让用户确认归属日，不能擅自推断。对结果不确定的请求先用原 request_id 对账，不能换 ID 重放。

验收：23:59 断网、次日同步、跨时区、重复同步、应用重启、账号切换、响应丢失；账单日期正确且只产生一条记录。

**A13—A14：统一“未知”和“撤销”语义。** 消耗不明用可表达未知的字段/来源，明确“0”与“未提供”区别；修订补录文案与统计口径。私密照片与私信媒体采用 no-store 或强制再验证，公共素材保留强缓存，社区缩略图按可见性策略配置。缩略图继承原图权限，清理时一并处理。

验收：界面说明、返回值、图表、CSV/JSON一致；在新请求下验证退出、撤销分享、注销、链接过期、下架后的访问行为，并明确已被用户保存到设备的内容无法远程收回。用真实浏览器验证 HTTP 缓存，单元测试检查响应头不算完成。

扩容决策：SQLite WAL 仍只有一个写入者，参见 [SQLite 官方 WAL 说明](https://www.sqlite.org/wal.html)。当前本机短测没有给出必须迁移数据库的证据。先减小查询量、缩短写事务，再用接近生产配置的混合负载测量锁等待与P95/P99。若持续达不到目标，再立项迁 PostgreSQL；迁移不能脱离后台 Directus、备份恢复与数据校验单独推进。进程内连接管理只能服务单进程的限制也见 [FastAPI 官方 WebSocket 文档](https://fastapi.tiangolo.com/advanced/websockets/)。

暂缓项目：重写原生App、微服务、复杂推荐引擎、商城会员、群聊、直播、自动动作识别。原生厂商离线消息推送和TURN TCP/TLS支持有实际价值，但应在基础链路稳定后单独评估接入成本、目标机型、后台权限与网络条件，先做专项验证再承诺可用范围。
