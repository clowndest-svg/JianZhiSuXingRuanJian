## 3. 原方案需要校正的重点

### R01：A14 需要同时验授权与缓存

隔离合成数据复现，结果见 [media-probe.json](audit-evidence-2026-10-23/media-probe.json) 和 [步骤](audit-evidence-2026-10-23/media-reproduction.md)：

1. 两个互相关注的临时账号发送图片私信，先保存返回的签名 URL。
2. 发送方成功撤回消息，撤回接口返回 200；随后新请求仍能用旧 URL 得到 200，返回原图字节相同，响应为 `private,no-store`。
3. 在该私信媒体 URL 上增加 `thumb=1`，响应变成 `private,max-age=300`。
4. 把受测路由看到的时间推进至签名到期前 1 秒，仍得到 `max-age=300`。

相关入口是 `server.py` 的 `signed_photo`、`private_photo`、`chat_recall`、`_message_dict`。当前没有 `audience` 的签名下载主要凭 HMAC、到期时间和文件存在判断，没有回查该条私信是否撤回；`thumb` 也没有被媒体用途授权约束。

必须修正文档中的两个等式：**不缓存不等于撤销授权；缓存时间小于签名总时长不等于缓存早于签名到期。** 应由业务媒体用途与引用关系决定授权，原图和派生图共用规则。若要求“撤回后立即拒绝新读取”，需要每次请求可验证的授权；若允许短时延迟，必须明确最长窗口并验它，不能默认为即时生效。

本次已经证实服务端行为，尚未实际测浏览器缓存重用、各类 HEAD/Range 与多设备。这些留在正式清单中。原图被用户另存或截图不属于可远程收回的范围。

### R02：B06 的模块三态与界面展示需要分别验

`app_modules/online_ai.py` 的配置、成功、失败状态及 `server.py` 的 `/api/ai/status` 已有实现；现有 8 项测试只测模块/状态函数。本次检索前端资产，未找到该接口及 `online_model`、`online_configured`、`online_last_success_at` 等字段的消费入口。

因此，阶段记录中“界面三态已完成”和文末“界面仍未做”不能同时作为当前结论。已统一为“服务端已有，UI 待实现/验证”。正式验收要实际看到未配置、已配置未成功、成功、失败后保留历史成功、恢复五种页面状态；不触发真实付费请求来伪造检查结果。

### R03：A06 的坏包用例没有独立构建三个反例

`test_optimization_gate_refuses_a_release_nobody_can_install` 先删除 APK、再修改清单哈希、最后改包内 JS 构建号，然后才遍历仅保存标签的 `cases`。循环中的三次检查看到的都是最后一份夹具，不能据三个标签宣称分别覆盖“包丢失、哈希错误、构建号错误”。本次未修改该测试，只把逐案构建/断言列为待办。

此外，文件存在、大小、哈希和 `assets/app.js` 的 APP_BUILD 一致，仅说明部分发布物一致；伪 APK ZIP 也可包含这些文件，不能据此声称“真实可安装”。AndroidManifest 的 versionCode、签名证书、真实升级安装与下载哈希须单独检查。联系不上主应用时 `confirmed:false` 也是未确认状态，界面不得报“生效成功”。

### R04：配置发布和跨仓 CI 仍需完整验收

当前后台打包与 `scripts/ci-deploy-server.py::deploy_admin` 仍只传送 `admin_api.py`、`console.html` 两个文件。新增配对检查没有自动把 systemd、sudoers、helper、Directus 策略和镜像配置一起发布，C03 应记为部分完成。

后台已填主仓精确 SHA `610f8b4...`，执行记录中的“占位值未填”已过期；但主仓 CI 新增的后台夹具仍按浮动 `main` 获取。后台 data/ux 契约接入只存在于当前未提交工作区，不能算远端流水线已守住。发布前应固定两仓完整 SHA 和配置/迁移版本，记录是哪一对通过，避免一侧 main 已变化后重跑出不同结论。本轮没有查询并确认最终 CI run 全绿。

降权应在隔离环境连同密钥权限、数据库 WAL/SHM、备份读取、邮件配置写入和 helper 调用一起测试；不能仅检查 unit 的 User 字符串。Directus 日常角色须用实际策略账号验证，超管测试不能代替。回退也应覆盖这些配置变更。

### R05：B08 与 C12 的模拟契约不能代替真实体验

`dm-state-call.mjs` 使用假 fetch、假 WebSocket；PWA 契约在 VM 中模拟 CacheStorage。本次运行通过可以证明相应客户端逻辑，不能证明真实双端通话、运营商网络、系统权限、浏览器升级中断与跨账号缓存行为。对应设备/浏览器格必须保持待验。

### R06：C09 需增加数据库与媒体的一致性条件

`scripts/backup.py` 先做 SQLite backup，再归档正在使用的 uploads。数据库完整性通过不能单独证明其引用的媒体也都属于同一逻辑快照。应确定写入/删除协调、引用清单或对象版本方案，并在恢复时逐引用验证；本轮只发现静态风险，没有声称生产备份已损坏。

Windows 拉回并解密成功只证明取得的那份副本可用；独立异地副本、电脑离线时仍能备份、丢失主机后的密钥恢复和 RPO/RTO 都需实际演练。

## 4. 图片、文件与 MinIO 的建议

**当前继续使用本地 uploads。** 现有媒体仅约 1.81MiB，机器还有空间和一定内存余量，没有证据支持现在为了存图片增加一个同机对象存储进程。优先正确授权、缩略图、按用途缓存、转换并发、备份与增长监控。

| 方案 | 解决的实际问题 | 本项目当前取舍 |
| --- | --- | --- |
| 本地磁盘 + 现有应用授权下载 | 最少常驻组件，复用已有转码与缩略图 | 当前选择；需补 A14 和备份边界 |
| 同机自建 MinIO | 提供 S3 API 与对象管理 | 磁盘/出口/宿主机故障域仍相同；目前收益不足以支持新依赖 |
| 独立主机自建 S3 服务 | 分离资源与运维边界 | 有自建需求后单独评估维护、许可、主机成本和恢复，不提前选型 |
| 托管对象存储 | 可承载独立异地副本或外部媒体分发 | 先考虑加密备份；在线媒体迁移待容量/流量证据和当前报价，不直接购买或配置 |
| CDN | 缓存与边缘分发 | 与存储分开评估；私密内容需明确鉴权与撤销，不能默认开放公共桶 |

截至本次查询，MinIO Community 官方仓库在 2026-04-25 被归档，并声明停止维护，旧二进制不再更新；不建议作为新生产依赖。AIStor Free 属于另一发行产品，本轮未验证其许可配置、实际资源占用和升级路径；不能照搬旧社区版部署教程，不能把企业集群推荐内存误称为小型单机最低需求。[官方仓库](https://github.com/minio/minio)

如后续使用云对象存储，存储只承担字节/对象管理，业务权限继续由应用负责。预签名 URL 属于持有者可使用的临时凭证，不能因为业务退出就假设已即时失效；S3 文档也说明签名可在有效期内重复使用。[官方预签名 URL 说明](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html)

上线前必须覆盖：私有桶与最小权限；上传大小/类型/真实解码/用户配额；缩略图、转码和 ASR；删除/共享引用/注销；清理任务幂等；Range/跨域/缓存；备份恢复；断网与对象存储故障。数据库保留稳定对象标识和引用，不保存临时签名 URL，不把 SQLite 数据库放到对象存储挂载上。

迁移仅在立项后执行：完整盘点 → 适配层 → 隔离样本 → 有界回填和校验 → 新写入切换 → 兼容旧文件读取 → 小流量切读 → 回退保留期结束后清理。独立备份不必等待在线媒体迁移；同桶复制或同机多目录不能自动算独立备份。

## 5. 结合当前机器的执行重点

1. **完成现有权限/数据边界。** 施工方处理 A14 与有效反例，补 B06 页面、跨仓流水线和配置发布。大规模样本仅在隔离库生成。
2. **建立整机预算。** 观察主应用、Directus、Redis、模型、ASR、TURN 与其他项目共同峰值；转换/推理排队有界、可超时。不要用服务硬限简单相加代替峰值测量，不因一次旧截图随意停别的项目。
3. **建立媒体和恢复基线。** 记录媒体/派生文件/备份实际空间、增长率、出站流量、失败清单与恢复时间；线上只监测，不压测。
4. **测量后决定扩容或存储迁移。** 先减少查询、缩短写事务、修无界任务；仍长期无法满足目标再比较加内存、迁外部存储和架构调整。保持单 worker，直到真实跨 worker 消息/呼叫/撤销通过。

资源初始目标与分档负载见方案 D01 和验收文档，属于待校准预算。未做持续混合负载前，不给“支持多少在线用户”的结论。
