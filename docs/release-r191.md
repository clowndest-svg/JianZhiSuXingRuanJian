# r191 / 2.4.2（75）：功能关联与记录一致性加固

目标：照片识餐与现有记餐、历史、统计、离线重试、账号及后台使用同一份业务数据；异常或并发操作不能重复记账、覆盖新版本或污染其他账号。保留既有产品入口和旧客户端兼容。

## 关联与执行方案

| 关联 | 统一行为与保护 |
| --- | --- |
| 照片、文字记餐 → 饮食流水 | 所有食材总量在服务端重算；业务记录和原始回执同一事务提交；失败整笔回滚。 |
| 网络重试、离线草稿 → 同一笔保存 | 相同标识和内容返回原回执；同标识不同内容返回409；成功后清除同一离线草稿。 |
| 今日记录、历史 → 修改/删除 | 提供记录版本；旧版本不能覆盖或删除其他页面/设备的新版本；冲突必须重载核对。 |
| 修改/删除 → 审计、当天汇总、完整日确认 | 审计与业务变更同一事务；回执内前后汇总与同一事务一致；完整日确认同步失效。 |
| 流水 → 首页、图表、习惯矩阵 | 每次多查询读采用同一SQLite快照，避免汇总与明细跨提交；前端只接收当前代次的最新刷新。 |
| 账号切换 → 请求及视图 | 旧账号迟到成功/失败不可覆盖当前状态，旧401不可清除当前令牌。 |
| 后台、备份、删号 → 新回执表 | 主应用拥有schema17；回执表关联用户并级联删除；后台动态用户引用与备份全表发现沿用。 |

实施顺序：核对调用链与现有数据口径；新增原子回执与版本冲突检查；整合前端重试与刷新；执行并发/故障/浏览器及关联回归；正式构建签包；经前后台CI、隔离QA与备份门禁部署；生产复验、临时账号清理及证据归档。

## 实现边界

schema17只新增record_write_receipts及审计查询索引，不重写旧食材、记录或密钥。旧客户端未传版本的修改仍保持兼容；新版今日/历史和照片入口传版本。新回执保护从本版本开始，历史request_receipts仅保留原有“已保存”回执，不编造历史记录ID或请求内容哈希。

版本基于记录内容与修改流水序号，即使数值改回原值，旧版本也不能覆盖。照片保存等待识别结束；回执不确定时冻结内容并使用原标识重试。发生版本冲突时只允许明确重新载入最新记录，不自动覆盖。

识别效果边界沿用r190：每项100g是待核对假设，有漏识与生熟误判可能，不用于照片称重。实体Android安装/相机授权仍需设备验收。
