# r193 / 2.4.4（77）：下载地址回到唯一真源

2026-11-06（UTC+8）。用户截图指出下载弹窗里仍然写着 `https://124.220.54.64/qingsu.apk`，而现役入口早已是 `https://scientificexploration.art`。

## 根因

弹窗里那四处"地址"各有各的来源，没有一个是真源：

| 出口 | 改之前 | 问题 |
| --- | --- | --- |
| 屏幕上显示的文本 | `index.html` 模板字面量 `https://124.220.54.64/qingsu.apk` | JS 从来不碰它——`href` 会被 `loadApkMeta()` 重算，可见文本永远停在写死那一刻 |
| 点下去的 `href` | `API_BASE + "/qingsu.apk"` 自己拼主机名 | App 内 `API_BASE` 默认是 IP，于是点击也走 IP |
| 「复制下载网址」 | 又一份 `API_BASE + "/qingsu.apk"` | 与屏幕上显示的可能不同，用户复制到的是第二个地址 |
| 二维码 | 包内静态 `assets/qr.svg` | 那张图 2026-10-16 的证据里解码出来就是 `https://124.220.54.64/qingsu.apk`，扫码直接进旧入口 |

一句话：**同一个下载动作在界面上有四个真源，就等于没有真源**。写死的那一份还特别会骗人——它不会报错，只会一直显示一个可能过期的地址。

## 改法

唯一真源定为服务器现算的 `version.json.apk_url`（`server.py` 按 `SITE_BASE` 生成；只有 `build<45` 且从 IP 入口取清单的老客户端才回落 IP，这条兼容分支保留并单独钉住）。四处出口全部从它取：

- `link.href = apk_url + "?v=" + sha256 前 12 位`，并且 `link.textContent = link.href`——**屏幕上写的就是点下去的那一条**；
- 模板里的绝对地址删掉，换成"下载地址读取中…"占位：JS 没跑之前屏幕上不允许出现一个可能过期的地址；
- `copyApkDownloadUrl()` 复制的是清单里那条（拿不到清单才回落 `API_BASE`），复制结果当场用 toast 说给用户；
- 二维码改为向服务器取 `/qr.svg?v=<指纹>`：它编码的就是这台服务器当前的入口，前端抄不出第二份地址；包内那张静态图只作离线兜底，并已重新生成为现役域名。

## 边界（本轮没动的）

App 内**接口请求**的主机名仍是 `app.js` 里 `API_BASE` 的默认值（IP）。它决定的是所有 API 流量、TLS 目标与 CORS 允许源，是另一件事：改它要单独评估旧客户端、证书链与备案状态，本轮没有顺手改。用户看到的、点的、复制的、扫的下载地址已经与它无关。

## 判据

`tests/download-link-ui.mjs`（真 Chromium + 真 uvicorn，14 条）：清单三条分支用 `Host` 头真打（`fetch` 会吞 Host，所以走裸 http）——现役客户端拿现役入口、`build<45` 且从 IP 入口拿清单仍回落 IP、新客户端即使从 IP 入口也拿现役入口；模板里不得出现任何绝对 APK 地址；`可见文本 == href`、`href` 以清单 `apk_url` 开头并带指纹；下载文件名与版本行取自清单真值；复制到的值 == 屏幕上的值；服务端二维码 == 按本站入口现算的点阵，且**不等于**包内那张静态图（正反样本同条内置，静态图只作兜底这件事因此是可证的）。

`tests/legacy-backend.py` 补 4 条静态判据并复跑 628 条全绿：模板/脚本里没有写死的绝对 APK 地址；可见文本跟着 href 走；复制走清单；包内 `qr.svg` 点阵必须等于域名生成、必须不等于 IP 生成（同一条里自带正反样本）。

有一条**旧判据是错的，已重写**：原来断言源码里出现 `link.href = API_BASE + "/qingsu.apk` 这种拼串写法——它钉的是实现细节而不是意图（意图是"取线上资源必须带源，不许用根相对路径"）。地址来源改成清单之后，这条在正确实现下恒红。现在钉的是"地址来自清单 `apk_url`、`API_BASE` 只作兜底、不许出现根相对赋值"。

变异标定 6/6 全部被抓：模板写死回 IP（浏览器 1 红 + legacy 2 红）、可见文本不再跟 href（2 红 + 2 红）、复制自己拼主机名（1 红 + 2 红）、包内二维码退回 IP（legacy 3 红，含那条反样本）、二维码不接服务端（1 红）、删掉老客户端回落 IP 的兼容分支（1 红）。

文档同步：`README.md` 入口块五条 IP 链接全部换成现役域名，并显式写明"IP 只是很旧客户端的兼容入口，`apk_url` 由服务器现算"——原来那块与它下面一句"已启用可信域名"自相矛盾，正是 C14 要防的那种。`.env.example` 的 `QINGSU_SITE_BASE` 示例、Android 冒烟夹具里的下载地址也一并换成域名。

## 顺带修掉的一条：首屏重复取数是"看运气"的

`tests/frontend-firstscreen.mjs` 在 r192 收尾时实测 25 个请求、无重复；本轮 r193 候选第一次跑就报
`红 接口与脚本不被重复请求 -> 2× /api/habits`、请求数回到 26。查下来不是判据漂了，是上一轮的修法不成立：
首屏有两个入口要这块 30 天矩阵（网页工作台初始化、仪表盘刷新后重绘），我当时只合并"同时在途"的那一次——
两条请求撞上就省一个，没撞上就各发一次。**同一个构建实测一次 25、一次 26**，这种"平均变好"不能算修好。

先试的是"按数据代次记账"（同一代只真取一次）。这条被既有判据拦住了：`legacy-frontend` 明确要
"每次显式调用都真取数、取数失败要把原因再说一遍"，代次缓存会把第二次调用直接吞掉，
`矩阵取数失败真的画出了原因` 当场变红。既有判据是对的，我那条是错的，于是换成更简单的确定性做法：

- 首屏只留一个取数入口（仪表盘刷新），工作台不再自己发一次；
- 仪表盘取数失败的那条路也调用渲染，屏上照样写"矩阵没取到数据：原因"，不静默空着；
- 写入之后的重绘仍走同一条路，真的重新取数。

复跑两次：`实测 25 个请求`、`接口与脚本不被重复请求` 两次都绿，`legacy-frontend` 全绿，
`frontend-budget` 34 条全绿。判据本身也是证据——它在修好之前真的红过一次，不是写完代码才补的绿灯。
